# 启动可用性测试说明

本文说明如何测量桌面端从启动到“功能可用”的等待时间，如何查看测试结果，以及各项指标的含义。

## 适用场景

这个测试用于验证下面两个现象：

1. 用户多久能看到 `Omni Translate` 主窗口。
2. 主窗口出现后，还要等多久才能完成前端 bootstrap，并进入可正常使用的状态。

注意：窗口出现不等于功能可用。测试会继续等待前端写出 `startup.readiness_ready` 标记，并检查 bootstrap 步骤是否有错误。

## 运行前准备

在仓库根目录执行：

```powershell
cd <repository-root>
```

确认没有旧的桌面壳进程或构建进程占用启动链路：

```powershell
Get-Process -Name omni-desktop-shell,cargo,rustc -ErrorAction SilentlyContinue
```

确认 Vite 默认端口 `4173` 没有被旧进程占用：

```powershell
Get-NetTCPConnection -LocalPort 4173 -State Listen -ErrorAction SilentlyContinue
```

如果普通 PowerShell 启动时报 `os error 740` 或提示需要提升权限，请使用管理员 PowerShell 运行测试。

## 运行完整启动测量

推荐命令：

```powershell
npm run perf:startup-readiness
```

如果需要手动传入参数，请直接调用脚本，避免 npm 在 Windows 下错误解析 PowerShell 参数：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\testing\measure-startup-readiness.ps1 -TimeoutSeconds 180
```

如果需要管理员权限：

```powershell
$script = (Resolve-Path .\scripts\testing\measure-startup-readiness.ps1).Path
Start-Process -FilePath powershell.exe -Verb RunAs -Wait -ArgumentList @(
  '-NoProfile',
  '-ExecutionPolicy',
  'Bypass',
  '-File',
  $script,
  '-OutputRoot',
  'artifacts/testing/startup-readiness',
  '-TimeoutSeconds',
  '180'
)
```

## 复用已运行的 Vite

如果 `4173` 上已经有 Vite dev server，并且你只想测 Tauri 窗口到前端 ready：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\testing\measure-startup-readiness.ps1 -UseExistingDevServer -TimeoutSeconds 180
```

默认模式会自动启动 `npm run dev:tauri --workspace @omni/desktop`，并要求 `4173` 空闲；`-UseExistingDevServer` 会跳过 Tauri 的 `beforeDevCommand`。

## 查看测试结果

每次运行会生成一个独立目录：

```text
artifacts/testing/startup-readiness/<run-id>/
```

关键文件：

1. `report.json`：机器可读的完整测试报告。
2. `report.md`：人可读摘要。
3. `tauri-dev.stdout.log`：Tauri/Vite 标准输出。
4. `tauri-dev.stderr.log`：Tauri/Cargo 错误输出。
5. `artifacts/diagnostics/logs/app.log`：应用诊断日志，包含 `startup.readiness_ready` 标记。

查看最新报告：

```powershell
$latest = Get-ChildItem .\artifacts\testing\startup-readiness |
  Sort-Object LastWriteTime -Descending |
  Select-Object -First 1

Get-Content -Raw (Join-Path $latest.FullName 'report.md')
```

验证最新报告是否达标：

```powershell
node .\scripts\testing\verify-startup-readiness.mjs
```

验证脚本测试用例：

```powershell
npm run test:startup-readiness
```

## 判定标准

当前硬性阈值：

```text
readiness.windowToReadyMs <= 10000
```

也就是：主窗口出现后，最多等待 10 秒必须进入功能可用状态。

这 10 秒进一步拆成下面几个预算：

| 阶段 | 指标 | 上限 |
| --- | --- | --- |
| 窗口出现到 React App 挂载 | `phases.windowToFrontendMountMs` | `1000ms` |
| React App 挂载到前端发出 ready signal | `phases.frontendMountToReadySignalMs` | `8500ms` |
| 前端 ready signal 到 native 日志落盘 | `phases.readySignalToNativeLogMs` | `500ms` |

前端 `8500ms` 预算继续拆分为：

| 前端步骤 | 指标 | 上限 |
| --- | --- | --- |
| 检测 Tauri 环境 | `frontendStepDurationsMs.detect-runtime` | `200ms` |
| IPC ping | `frontendStepDurationsMs.check-ipc` | `1000ms` |
| runtime 初始化 | `frontendStepDurationsMs.init-runtime` | `1500ms` |
| 音频初始化 | `frontendStepDurationsMs.init-audio` | `3000ms` |
| 配置加载 | `frontendStepDurationsMs.load-config` | `2400ms` |
| 启动遮罩完成展示延迟 | `frontendStepDurationsMs.bootstrap-overlay-delay` | `400ms` |

以下情况都算失败：

1. 没有检测到主窗口。
2. 没有检测到 `startup.readiness_ready`。
3. `readiness.windowToReadyMs` 超过 `10000ms`。
4. 前端 bootstrap 任一步骤出现 `errorAtMs`。
5. 启动前环境不干净，例如 `4173` 被占用，或已经有 `omni-desktop-shell.exe` 在运行。
6. Tauri/Rust 构建失败，或需要管理员权限但没有提升权限。

## 重要指标

### `window.detectedElapsedMs`

从脚本启动命令开始，到 Windows 检测到标题为 `Omni Translate` 的主窗口为止。

这个指标回答：用户多久能看到窗口。

### `readiness.detectedElapsedMs`

从脚本启动命令开始，到应用诊断日志出现 `startup.readiness_ready` 为止。

这个指标回答：从启动到前端认为 bootstrap 结束，总共用了多久。

### `readiness.windowToReadyMs`

计算方式：

```text
readiness.detectedElapsedMs - window.detectedElapsedMs
```

这个指标回答：窗口出现后，用户还要等多久才能使用功能。

这是当前测试的核心指标，必须小于等于 `10000ms`。

### `readiness.frontend.readyAfterAppMountMs`

从 React `App` 挂载开始，到启动遮罩结束的前端内部耗时。

这个指标不包含 Vite、Cargo、Tauri 进程启动、窗口创建等外部耗时。它适合定位前端 bootstrap 本身慢在哪里。

### `readiness.frontend.steps`

前端 bootstrap 各步骤耗时：

1. `detect-runtime`：检测是否处于 Tauri 桌面环境。
2. `check-ipc`：调用 `debug_ipc_ping` 检查 IPC 通道。
3. `init-runtime`：初始化 runtime snapshot 和事件监听。
4. `init-audio`：初始化音频设备与音频 runtime。
5. `load-config`：加载配置草稿。

每个步骤可能包含：

1. `activeAtMs`：步骤开始时间，单位 ms，起点是 React `App` 挂载。
2. `doneAtMs`：步骤成功完成时间。
3. `errorAtMs`：步骤失败时间。
4. `detail`：步骤附带信息或错误摘要。

只要任一步骤出现 `errorAtMs`，报告就不能算功能可用。

## 当前一次实测样例

最近一次管理员 PowerShell 实测报告：

```text
artifacts/testing/startup-readiness/startup-readiness-20260608-080743-9dc97d76/report.json
```

结果摘要：

```text
window.detectedElapsedMs = 32857ms
readiness.detectedElapsedMs = 54040ms
readiness.windowToReadyMs = 21183ms
readiness.frontend.readyAfterAppMountMs = 8450ms
verdict = bootstrap-error-before-ready
```

这次不达标，原因有两个：

1. 窗口出现后到 ready 用了 `21183ms`，超过 `10000ms`。
2. bootstrap 走了错误路径：`check-ipc` 在约 `8060ms` 时出现 `IPC 通道未响应`，后续 `init-runtime`、`init-audio`、`load-config` 也都进入 error。

因此这次不能解释为“21 秒后功能可用”，只能解释为“21 秒后错误路径结束，功能未正常 ready”。

进一步拆解这次耗时：

| 阶段 | 实测 | 结论 |
| --- | ---: | --- |
| Vite ready | `1162ms` | 正常，不是主要问题 |
| Cargo dev build | `24820ms` | 导致“看到窗口前”等待很长 |
| 启动到窗口出现 | `32857ms` | 主要受 Cargo build 和 Tauri 启动影响 |
| 窗口出现到 React App 挂载 | 约 `417ms` | 在 `1000ms` 预算内 |
| React App 挂载到前端 ready signal | `8450ms` | 接近 `8500ms` 上限，但它是错误路径 |
| ready signal 到 native 日志落盘 | 约 `12312ms` | 严重超过 `500ms` 预算 |
| 窗口出现到 native ready marker | `21183ms` | 严重超过 `10000ms` 总预算 |

同一时间段的 `app.log` 显示：

1. `08:08:24.730` 左右 `debug_ipc_ping` 实际已经返回成功。
2. 随后出现两轮 `refresh_bridge_runtime`，都在等待 `\\.\pipe\omni-bridge-ipc`。
3. 第一轮 Bridge pipe 等待大约从 `08:08:24.917` 到 `08:08:31.956`。
4. 第二轮 Bridge pipe 等待大约从 `08:08:31.983` 到 `08:08:38.533`。
5. `startup.readiness_ready` 到 `08:08:38.561` 才写入日志。

这说明窗口后的长等待至少包含两个问题：

1. 前端 bootstrap 存在错误/重复路径，导致 `check-ipc` 被记录为超时，不能视为正常 ready。
2. Bridge 自动刷新在 ready 前后等待缺失的 named pipe，每轮约 6.5-7 秒，两轮叠加明显拖慢 ready marker 落盘。

## 常见失败与处理

### `dev-port-in-use`

含义：`4173` 已经有进程监听。

处理：

```powershell
Get-NetTCPConnection -LocalPort 4173 -State Listen -ErrorAction SilentlyContinue
```

关闭旧 Vite，或使用 `-UseExistingDevServer`。

### `desktop-shell-already-running`

含义：已有 `omni-desktop-shell.exe` 正在运行，无法测干净的首次启动。

处理：

```powershell
Get-Process -Name omni-desktop-shell -ErrorAction SilentlyContinue
```

关闭旧窗口后重跑。

### `os error 740`

含义：启动桌面壳需要管理员权限。

处理：使用管理员 PowerShell 跑测量脚本。

### `bootstrap-error-before-ready`

含义：检测到了 ready marker，但前端 bootstrap 中有错误步骤。

处理：优先看 `readiness.frontend.steps`，定位哪个步骤有 `errorAtMs`。例如 `check-ipc` 超时通常说明前端无法通过 Tauri IPC 调用 Rust command。

### `readiness-threshold-failed`

含义：bootstrap 没有错误，但 `windowToReadyMs` 超过 10 秒。

处理：查看 `readiness.frontend.steps` 哪个步骤耗时最长，再结合 `app.log`、`tauri-dev.stderr.log` 定位 Rust command、音频枚举、配置加载或自动启动流程。
