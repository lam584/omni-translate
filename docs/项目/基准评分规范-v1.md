# 基准评分规范 v1

## 目的与适用范围

本规范定义 Omni Translate 的实时音频基准测试评分。每个可评分结果均携带 `benchmark-score/v1`，因此仅可与相同版本的结果比较。旧版评分不会被迁移或并列展示。

评分用于解释一次基准运行的质量、响应速度、完成程度和运行稳定性；它不是模型在所有语言、音频、网络环境下的绝对排名。

## 正式评分的前提

正式总分必须同时满足以下条件：

- 基准运行已完成，且不是失败或中断状态。
- 四个维度都有完整的原始证据。
- 语义质量同时具有可验证的参考译文和成功的 LLM 裁判结果。

任一条件不满足时，界面会显示“评审中”“证据不足”“裁判失败”或“基准失败”，保留已有维度的明细，但不会对缺失维度重新分配权重，也不会给出正式总分。

## 总分、权重与等级

总分为四个维度的加权平均，四舍五入到一位小数：

| 维度 | 权重 |
| --- | ---: |
| 语义质量 | 40% |
| 时延 | 30% |
| 完整性 | 20% |
| 稳定性 | 10% |

等级为：A（90–100）、B（80–89.9）、C（70–79.9）、D（60–69.9）、F（低于 60）。

## 维度定义

### 语义质量

语义质量由两部分组成：

- 参考译文分占 40%。使用 chrF2：对文本做 Unicode NFKC 规范化并移除空白；保留大小写和标点；分别计算字符 1 至 6 gram 的精确率和召回率，再对各阶精确率与召回率分别取算术平均，并以 beta=2 计算最终 F 分数。结果会显示精确率、召回率和 chrF2 分数。
- LLM 裁判分占 60%。裁判对每个有效 run 的原文、参考译文和候选译文，分别给出 0–100 分的语义忠实度、术语/事实/数字、遗漏与无依据增译、语言流畅度；四项等权平均。裁判还必须返回简短理由、关键错误及其文本证据。

多个有效 run 分别计算后取平均。裁判模型名称与量表版本会记录在结果中；API Key 或其他凭据不会保存或导出。

量表锚点：90–100 表示没有实质性问题；70–89 表示存在局部但不改变整体可用性的错误；40–69 表示有明显含义、术语、遗漏或表达问题；0–39 表示严重失真、重要内容缺失或大量无依据内容。

### 时延

每个有效 run 都计算从 `responseCreated` 起算的两项时延：

- 首字时延：不高于 2 秒得 100 分，达到或超过 8 秒得 0 分，中间线性插值。
- 首个完整译文时延：不高于 5 秒得 100 分，达到或超过 15 秒得 0 分，中间线性插值。

两项以及所有有效 run 的分数取算术平均。界面会展示每项实际毫秒数、阈值区间和该信号的分数。任一必需事件缺失时，这个维度不具备正式评分资格。

### 完整性

`完整性 = 100 × 完成且具有最终译文的 run 数 / 声明 run 数`。

界面会列出完成数、声明总数，以及每个未完成 run 缺少的响应完成事件或最终译文。

### 稳定性

`稳定性 = clamp(100 × 成功 run 数 / 声明 run 数 − 5 × 额外响应总数, 0, 100)`。

一个 run 的第一条响应不扣分，后续每一条响应均为额外响应并扣 5 分。明细会显示基础成功率、失败 run 和每笔扣分。

## 状态与证据

评分结果记录独立的运行状态和评分状态。运行可以是运行中、已完成、失败或已中断；评分可以是待评审、评审中、正式、证据不足或裁判失败。历史记录保存报告和评分证据，以便重新查看“为什么低”。

| 评分状态 | 含义 | 是否有正式总分 |
| --- | --- | --- |
| `benchmark-running` | 基准尚未完成。 | 否 |
| `judging` | 基准完成，语义裁判正在处理。 | 否 |
| `evidence-insufficient` | 原文、参考译文、逐 run 裁判、时延事件或其他必需证据缺失。 | 否 |
| `judge-failed` | 已尝试自动或手动裁判，但请求或结构化响应失败。可重试或更换裁判模型。 | 否 |
| `benchmark-failed` | 基准运行失败或启动后被中断。 | 否 |
| `official` | 四个维度均有完整证据，按本规范得出总分和等级。 | 是 |

对于自定义音频，如果没有可验证的原文与参考译文，系统会保存基准记录，但语义维度和正式总分均为证据不足。

## 历史记录、导出与秘密

v1 记录保存在独立的本地 SQLite `benchmark_history` 表中；配置保存、重置和导入不会清空它。记录在开始时建立，在完成、失败、自动裁判和手动重试时更新同一记录。应用下次启动时，遗留的“运行中”记录会标为“已中断”。

历史列表按创建时间倒序分页（默认每页 50 条）。删除单条或清空历史都要求用户确认。JSON 与 TXT 导出均包含完整原始 benchmark report 和完整 `BenchmarkScoreV1` 对象；历史详情可使用相同导出格式。

系统不会保存 API Key、Authorization、密码、token 或其他凭据。持久化层会递归移除凭据形字段；疑似包含凭据的错误文本会被替换为脱敏提示。

## 版本兼容政策

评分对象的 `schemaVersion` 与 `version` 都必须为 `benchmark-score/v1`。历史 API 只接受该版本，不会扫描、导入或迁移旧评分文件或旧内存结果。今后的评分规则变更必须使用新版本标识；不同版本只能分别查看，不能将数值作为同一量表横向比较。

## 示例

若语义、时延、完整性、稳定性分别为 80、75、100、90，则正式总分为：

`80 × 0.4 + 75 × 0.3 + 100 × 0.2 + 90 × 0.1 = 83.5`，等级为 B。

若其中任一维度缺失证据，则不会将其余维度放大为总分，而会显示缺失原因。
