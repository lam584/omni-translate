# 测试与质量门禁

## 1. 适用范围

本文面向开发人员，说明如何在本机手动运行项目测试、配置真实 LLM/音频集成测试密钥、查看测试产物和判断结果。

覆盖范围：

1. 前端单元测试与覆盖率。
2. Bridge Service 测试。
3. Tauri/Rust 桌面壳测试。
4. DashScope 文本模型与 Omni Realtime 音频集成测试。
5. 统一质量门禁与手工 E2E、性能基线、安装回归记录模板。

## 2. 测试前准备

1. 在仓库根目录执行命令：

```powershell
cd <仓库目录>
npm install
```

2. 确认 Rust toolchain 可用：

```powershell
cargo --version
```

3. 确认音频集成测试文件存在：

```powershell
Test-Path .\scripts\testing\fixtures\watch-mode-en-original.wav
```

4. 确认 LLM 集成测试配置文件存在：

```powershell
Test-Path .\scripts\testing\llm-integration.config.example.json
```

## 3. 配置密钥

LLM 与音频集成测试读取 [llm-integration.config.example.json](E:/omni-translate/scripts/testing/llm-integration.config.example.json)。

推荐做法是把真实密钥写入本机环境变量，不把密钥提交到仓库：

```powershell
$env:OMNI_TEST_DASHSCOPE_API_KEY = "sk-替换为你的DashScopeKey"
```

如果需要让测试脚本自动注入密钥，也可以在配置文件中保留本机专用的 `environment` 段：

```json
{
  "environment": {
    "OMNI_TEST_DASHSCOPE_API_KEY": "sk-替换为你的DashScopeKey"
  }
}
```

当前集成测试会使用：

1. 文本翻译模型：`providers[].model`，当前为 `qwen3.6-flash`。
2. 音频模型：`audio.model`，当前为 `qwen3.5-omni-flash-realtime`。
3. 音频文件：`audio.testFile` 或 `audioTestFile`，默认使用 `./scripts/testing/fixtures/watch-mode-en-original.wav`。

## 4. 一键运行所有测试

运行全部自动测试，包括前端、Bridge Service、Rust/Tauri、DashScope 文本和音频集成测试：

```powershell
npm run test:all
```

如果本机没有可用 DashScope 网络或密钥，只跑不依赖外部服务的测试：

```powershell
node ./scripts/testing/run-all-tests.mjs --skip-integration
```

`test:all` 只负责执行测试并在终端显示结果，不生成质量门禁归档。需要归档日志和手工检查模板时，使用 `npm run quality:gate`。

## 5. 单项测试命令

常用命令：

```powershell
npm test --workspaces --if-present
npm run test:desktop-shell
npm run test:llm-integration
npm run test:desktop-coverage
npm run test:watch-mode-evidence
npm run quality:gate
```

命令说明：

1. `npm test --workspaces --if-present`：运行所有 npm workspace 中定义的测试；生产桥接链路只保留 native bridge Rust 测试。
2. `npm run test:desktop-shell`：运行 Tauri/Rust 测试；默认会跳过 ignored 的真实 LLM 集成测试。
3. `npm run test:llm-integration`：单独运行 ignored 集成测试，真实调用 DashScope 文本模型和 Omni Realtime 音频模型。
4. `npm run test:desktop-coverage`：生成桌面前端覆盖率。
5. `npm run test:watch-mode-evidence`：校验最新完整 Watch Mode live report 是否通过；只读取 artifacts，不启动真实硬件链路。
6. `npm run quality:gate`：运行发布前质量门禁并生成归档产物；不强制运行 Watch Mode live。

## 6. 集成测试行为

`npm run test:llm-integration` 会：

1. 读取 `scripts/testing/llm-integration.config.example.json`。
2. 将 `environment` 段写入当前测试进程环境变量。
3. 设置 `OMNI_LLM_TEST_CONFIG` 指向配置文件。
4. 调用文本翻译 smoke 测试。
5. 解码原创 WAV 测试素材为 16 kHz mono PCM。
6. 通过 DashScope Realtime WebSocket 发送音频帧。
7. 断言收到转录、翻译或 `response.done`。

该测试依赖外部网络和 DashScope 额度，耗时通常明显长于本地单测。

## 7. 查看结果

普通测试结果直接看终端：

1. 成功：出现 `passed`、`ok` 或 `test result: ok`。
2. 失败：命令非 0 退出，并打印失败测试名、panic、断言或上游 API 错误。
3. Rust 输出中 `ignored` 不代表失败；LLM 集成测试需要通过 `npm run test:llm-integration` 单独运行。

质量门禁产物位于：

```text
artifacts/logs/testing/quality-gate/<timestamp>/
```

重点查看：

1. `quality-gate-summary.json`：自动化步骤、命令、日志路径和手工模板路径汇总。
2. `verify-desktop.log`
3. `coverage-desktop.log`
4. `check-desktop-shell.log`
5. `test-desktop-shell.log`
6. `contracts.log`
7. `check-bridge-service-native.log`
8. `test-bridge-service-native.log`

前端覆盖率产物由 desktop workspace 的 coverage 配置生成；通常先从 `coverage-desktop.log` 里确认实际输出路径。

## 8. 手工测试模板

生成桌面 E2E 手工测试记录：

```powershell
npm run smoke:desktop-e2e
```

输出目录：

```text
artifacts/testing/manual-e2e/
```

生成性能基线空白模板（仅用于查看 schema，不能手填数值作为发布证据）：

```powershell
npm run perf:desktop-baseline
```

输出目录：

```text
artifacts/testing/perf-baseline/
```

生成安装回归记录：

```powershell
npm run test:install-regression
```

输出目录：

```text
artifacts/testing/install-regression/
```

`npm run quality:gate` 会自动生成上述三类模板，并把路径写入 `quality-gate-summary.json`。

三类发布工件现在都要求：当前检出的 Git `HEAD` 完全一致、工作区干净、生成时间不超过 14 天，并且引用内容哈希未变化的来源收据。任意旧版 PASS 文档、祖先提交、dirty/untracked 源码状态或被修改过的收据载荷都会被拒绝。

`collect-release-manual-evidence.mjs` 已改为 fail-closed 兼容入口，不再接受任何调用方提供的 `--source`。authority package 只能由场景专用 production runner 在同一进程内完成原始工件校验后通过私有入口组装：

```powershell
node .\scripts\testing\run-desktop-release-evidence.mjs --scenario-id E2E-PROVIDER-CONFIG
node .\scripts\testing\run-desktop-release-evidence.mjs --scenario-id E2E-PROVIDER-PROBE
node .\scripts\testing\run-desktop-release-evidence.mjs --scenario-id E2E-DIAGNOSTICS-EXPORT
npm run collect:release-evidence:real-device-audio
node .\scripts\testing\run-overlay-click-through-release-evidence.mjs --operator "<操作者>" --operator-notes "<观察结果>"
npm run collect:release-evidence:virtual-mic
node ./scripts/testing/archive-release-manual-evidence.mjs --scenario-id <场景ID> --source <collector返回的packageDirectory>
```

通用 archive 不再接受任意文件、`observation.json` 或自报 PASS。manifest 固定绑定场景、authority emitter ID/version、artifact kind、载荷角色/文件名/hash、assembler 脚本 hash、当前 exact clean HEAD、采集时间窗和从原始工件重算的摘要；archive 复制前和发布 validator 读收据时都会再次校验。没有注册 production emitter 的场景会在解析调用者自写 schema 字段之前直接 fail-closed，并保持 manual pending。Provider 配置、Provider 探针和 diagnostics export 也不允许使用通用 `--source` 组装：专用 npm 命令先重建并嵌入当前 Git commit，再只启动一个 production Desktop，等待该进程 renderer 完成 `debug_ipc_ping`，在同一 `AppHandle` 内调用既有 storage/provider/diagnostics handler，并交叉验证 compile-time commit 等于当前 exact clean HEAD、Desktop PID、可执行文件 hash、invocationId、完整 diagnostics bundle 和固定 payload 后才进入 assembler。

当前 6 个 manual E2E 场景均有专用 production authority：3 个同进程 Desktop emitter（Provider 配置、Provider 探针、diagnostics export）、canonical strict schema-v6 真机音频 assembler、真实 Win32/WebDriver overlay click-through runner，以及 native `omni-virtual-mic-target-capture/0.1.0`。Provider 场景要求真实持久化配置和 Windows Credential Manager 中已存在的引用；probe 的 `available` 必须由 production handler 按 1200 ms 预算、真实 streaming、四项 checks 和 routing decision 重算。diagnostics full export 的十个固定文件会逐个按 schema/kind 校验，并从五份 snapshot 重新生成 summary。真机音频固定重验当前 exact clean HEAD 的完整 strict authority；overlay 固定绑定独立目标窗口、Win32 命中/输入/前后台 timeline、截图和工具链。五个 install 场景也只允许 canonical install runner。real-device/install 的公开入口会自行执行 canonical runner，不接受调用方提供的 raw source；私有组装入口还会通过 `Win32_Process` 绑定当前 Node PID、ExecutablePath、CommandLine 中唯一的 canonical runner 入口及 runner hash。`node -e`、`node -p`、stdin 脚本、非空 `NODE_OPTIONS`、generic `--source`、替换 manifest、dry-run、模拟和 skip 均不可进入组装器。测试中的 `test-fixture` authority 只用于 validator 单元覆盖，production CLI、archive 和默认 validator 都拒绝。

将命令返回的 `receiptPath` 和 `receiptSha256` 写入对应的固定场景。E2E 必须完整包含 6 个场景，安装回归必须完整包含 5 个场景，不能增删或乱序。`E2E-VIRTUAL-MIC-CAPTURE` 采用 capability-driven 验收，但稳定版 PASS 只接受 `supported=true`、`status=ready`、非空 `captureEndpointName` 和 `48000Hz/mono/pcm16`。validator 严格绑定 `omni-virtual-mic-target-capture/0.1.0`，交叉比较 collector/capture child/Bridge 三个互异 PID、protocol v6、Bridge instance/session、endpoint ID/name、raw before/after counters 与重算 delta、raw status timeline 与 cue lifecycle、WAV hash/frame count 和 fingerprint；virtual delta 必须大于 0、physical delta 必须为 0、queued→started→completed 必须 exactly-once。probe 与 runtime snapshot 还必须共同携带注入前 24000 个 PCM16 样本（严格 96000 个小写十六进制字符）及 SHA-256。统一 authority 会先重算 expected PCM hash，再扫描整份 WAV，要求仅存在一个全长窗口、每个样本量化误差不超过 1 LSB，并独立验证 997 Hz 频谱；声明的 `detected` 和 `startFrame` 不能代替重算。缺少 expected PCM 本体的旧三件套会 fail-closed，必须用当前二进制重新采集。`unsupported`/`failed` 只能作为明确不可用诊断，不能让三路线稳定发布场景通过。

真实性能基线必须先完成严格 Watch 矩阵。每个 live 单元会为 Desktop 根进程及其子进程写入逐秒 `system-metrics.json`：

```powershell
npm run test:watch-mode-live:production-coordinator -- -- --workers-config artifacts/testing/watch-mode-local-worker.json --runtime-authority artifacts/testing/watch-mode-strict-runtime/<release>/strict-runtime-authority.json --local-isolation-authority artifacts/testing/watch-mode-local-isolation/<run>/local-isolation-manifest.json
node ./scripts/testing/assemble-performance-baseline.mjs --operator "<操作者>"
```

assembler 只接受当前仓库、同一 clean HEAD 上的 schema v6 预算平衡 canonical authority；production CLI 不允许替换 workspace root。组装和发布校验都会重新执行完整 strict authority 验证，verification receipt 只作为索引，不能单独成为权威。归档会按路径、字节数和 SHA-256 绑定 canonical manifest、strict source manifest、strict verification receipt、每单元 authority receipt，以及 4 份付费 live `report.json`、`system-metrics.json` 和 `evidence-driven-terminal.json`；3 个零 LLM 本地格由独立 local-isolation manifest 绑定。Watch v11 的 4 个付费格仅使用精确模型 `qwen3.5-livetranslate-flash-realtime`；2 个 ordinary 格每格正常媒体时长为 `128.8153125s`，2 个 process-exclusion 格每格为 `173.8153125s`，合计 `605.26125s`。validator 会从 raw cue 时间戳重算 provider/字幕 commit p95，并从严格授权的报告和原始进程树采样独立重算字幕 TTS 首次播放延迟、CPU p95 最大值、内存峰值、全部 dropout；性能阈值要求 4 个付费格的 receipt-bound terminal 覆盖率为 100%，不再从已取消的 cell duration 推导稳定时长。唯一的 process-exclusion `model-stability` 格仍必须完成 input-complete、Provider `session.finished`、最后 cue receipt、本地连续静默和 immutable report 终态，而不是依赖固定 3 分钟成功下限。旧 schema、自报 canonical PASS、缺 receipt/hash/raw、summary 与 raw 不一致、或只重新哈希 `performance-source.json` 的输入都会 fail-closed。

## 9. 发布前建议流程

推荐顺序：

1. 配置 DashScope API Key。
2. 运行 `npm run test:all`。
3. 运行 `npm run quality:gate`。
4. 完成固定的 `manual-e2e`、严格矩阵性能组装和 `install-regression`，并为每个手工场景归档来源收据；不要手填性能数字。
5. 如需发版，再进入 release/installer 流程。

`release:verify` 会在普通质量门禁后额外执行 `npm run test:watch-mode-evidence:strict`。如果该步骤失败，必须通过 `npm run test:watch-mode-live:production-coordinator` 重新生成当前 exact clean HEAD 的完整 canonical strict authority，再按 `failureLayer` 定位问题；单次 live diagnostic、旧 `test:watch-mode-live:matrix` 入口和历史通过样例都不能替代正式发布证据。

任一自动化步骤失败时，不要只看最后一屏输出；先打开对应日志或终端失败段，确认是本地依赖、编译错误、断言失败、网络错误还是上游模型错误。
